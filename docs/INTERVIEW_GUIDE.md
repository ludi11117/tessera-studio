# 工程证据与面试讲法

## 90秒网页演示

现在可在主流程直接展示推荐解释：选一次A/B，看“上次选择后推荐发生了什么”，再展开属性分数贡献和真实训练曲线。可手算某个新旧属性权重之差，并验证各项之和等于推荐分数差。解释训练损失下降只说明拟合已有反馈，不保证新样本泛化；无反馈时没有曲线，当前方案并列最优时也不强推新设计。这些边界同样属于你需要理解的实现。

1. 打开 `/web-studio`，填入明确标为虚构的演示资料，选择一个设计方向。
2. 直接点导航，分别保留布局与色调；切换其他方向，展示导航属性不变，其他组件可以改变。
3. 点首屏，在布局×色调矩阵预览，再采用；展示修改收据和撤回。
4. 核对当前版本，导出 ZIP，离线打开 index.html。说明四组件 Schema、数据到 HTML 的编译边界、属性保护及 revision 事务各自解决什么问题。

网页技术细节见 [WEB_ARTIFACTS](WEB_ARTIFACTS.md)。算法追问结合 [实际重训实验](RETRAINING_STUDY.md)：72条策略轨迹、456次实际拟合，4条共同初始反馈加6条新增；新措辞中决策价值较好，原措辞中没有稳定优势，深度模型未超过线性对照。可以解释共同随机数、配对种子区间、泛化测试及固定假设推演和真实重训之间的偏差，避免声称训练通用模型。

真实用户价值需使用 [待实施对照协议](DELIVERY_BENCHMARK.md) 采集，当前无完成率或节约时间结论。简历可写“实现属性级保留和版本化交付，设计并完成合成反馈下实际重训对照实验”，不要填未经测量的产品提升比例。

这份文档只做一件事：把代码里已经实现的后端与算法机制，翻译成面试时能讲清楚、能被追问的回答。配套的实时页面是 `/proof`，源码入口是 `proof.py`。

先说边界：这是一个本地优先的单机应用，不是分布式系统，也不是自研大模型。能讲的是**提交协议、审计一致性、有限约束求解、精确编辑和模型作业治理**；不能讲成“任意任务自动交付”或“密码学防篡改”。

## 30 秒版本

> 我做了一个本地 AI 创作工作室。模型只负责生成候选文字，真正的提交、约束和交付由本地程序控制。比如多个窗口同时改一份稿，服务端用 revision CAS 在 `BEGIN IMMEDIATE` 事务里复核，旧版本会得到真实的 409；条件冲突时，我把 3⁴ 个候选枚举成位集，求交过滤，再删除条件得到不可再删的冲突核，并给每种最小修正附上候选证据。局部改写只接受模型返回的替换片段，服务端按 Unicode 码点拼接，并用前缀、后缀和选区三段哈希拒绝过期请求。整条链路有事件快照和测试，`/proof` 页面可以现场复现。

## 故事一：两个窗口同时提交，为什么不会互相覆盖

**面试官可能问**：并发编辑你怎么处理的？

**回答**：

> 每次读取会话时拿到一个 `revision`，提交时必须带上它。服务端在 `BEGIN IMMEDIATE` 事务里重新读取 revision，不匹配就抛 `Conflict`，HTTP 层映射成 409，并在响应里带 `request_id`。客户端收到 409 后重新拉取当前版本，而不是重试覆盖。这样两个标签页同时改一份稿，后到的请求会失败，不会把先到的改动静默吃掉。

**代码证据**：

- `store.py` 的 `Store.transaction()`：连接、`BEGIN IMMEDIATE`、提交/回滚、关闭。
- `store.py` 的 `Store.action()`：入口先校验 `body["revision"]` 与当前 revision。
- `server.py` 的异常映射：`Conflict` → 409，`Invalid` → 400，响应包含 `request_id`。

**取舍**：

- 单机 SQLite 下这是最便宜的正确做法；`BEGIN IMMEDIATE` 让写事务串行化，避免读后写竞争。
- 这不是分布式锁。多进程/多机部署要换成数据库行版本或带 fencing token 的租约；`revision` 语义可以保留，但事务边界要重做。
- 409 不是“请求格式错误”，而是“你基于旧状态提交”；把两者分开，客户端才能正确恢复。

**追问：为什么不用数据库自增版本做乐观锁？** 现在用的就是版本号 CAS，只是版本由应用层维护并写进每次事件；迁移到 Postgres 时可以直接换成 `UPDATE ... WHERE revision = ?`。

## 故事二：事件链如何支撑撤回、审计和训练标签

**面试官可能问**：你怎么保证历史记录可信？撤回会不会把后面的记录弄乱？

**回答**：

> 每个可变更操作都会追加一条事件，保存操作前后的完整状态快照和 revision；撤回不是删除历史，而是追加一条 `undo` 事件，读取时通过活动事件集合把被撤回的事件过滤掉。`/proof` 里的校验器会检查五件事：前后快照是否首尾相接、revision 是否单调 +1、事件序号是否严格递增、训练标签是否只出现在明确的 `compare` 事件、撤回目标是否存在且已失效。任何一项不满足都会显示红色。

**代码证据**：

- `store.py` 的 `Store.event()`：写入 `before_state`、`after_state`、`revision`。
- `store.py` 的 `Store.active()`：根据 `undo` / `feedback_retract` 过滤活动事件。
- `proof.py` 的 `chain_report()`：五项链校验，返回逐事件快照哈希。
- `store.py` 的 `Store.action()`：普通选择、编辑、AI 采用都会记录事件；训练标签只由明确的比较路径写入。

**取舍**：

- 这是本地一致性和可审计性，不是密码学不可篡改。能改 SQLite 文件的人也能改历史；要防篡改需要签名链或外部只追加存储。
- 保存完整快照会占空间；当前任务规模很小，换来了撤回和审计的简单实现。更大规模应改为增量事件 + 定期快照。
- 偏好标签只来自用户明确比较，点击推荐、查看方案、AI 输出都不算标签。这是数据质量问题，不是 UI 细节。

**追问：撤回后 revision 会回退吗？** 不会。撤回是新事件，revision 继续 +1，历史不可变；被撤回的状态只是在“活动视图”里失效。

## 故事三：条件无解时，怎么解释“为什么”和“改哪一条”

**面试官可能问**：用户同时要求锁定某章、必须保留一句话、还要压到 180 字，系统怎么处理？

**回答**：

> 先把当前任务的全部候选组合枚举出来，最多 3⁶ = 729 个；每个硬条件生成一个位集，表示哪些候选满足它，所有条件按位与就得到可行集合，这一步是精确的。无解时，我用删除法找一组不可再删的冲突条件：从全部条件开始，逐条尝试删除，如果删除后仍然无解就永久删掉，最后留下的集合里拿掉任何一条都会有解。然后我再从每个失败集合里取一个候选作为见证，去掉严格超集，得到包含关系最小的修正集合；最后逐条移除条件做敏感度分析。整个过程不调用模型，毫秒级完成。

**代码证据**：

- `ai/decision.py` 的 `analyze()`：候选枚举、约束位集、交集、前沿、冲突核、修正集合、敏感度。
- 关键实现：`masks` 每个条件一个位集，`intersection()` 做按位与；`eligible_bits.bit_count()` 得到可行数。
- `fail-closed` 交叉检查：分析器算出的可行集合必须与 `recommendations()` 完全一致，否则直接报错，避免两套搜索悄悄分叉。
- `/proof` 的默认条件就是冲突的：锁定「实现方法」第一版 + 必须保留「无需付费API」→ 0 个可行搭配，冲突核两项，最小修正两组。

**取舍**：

- 这是有限候选空间上的精确求解，不是通用 SAT/ILP，也不是连续文本空间的最优解。候选数随章节和版本指数增长，当前规模（3⁴–3⁶）适合穷举；再大就要换 CP-SAT / 分支定界，并重新定义“可解释性”。
- 冲突核是删除式结果，不保证条件数最少，也不代表只有一处冲突。修正集合是包含关系最小，不是最小基数。
- 敏感度各项新增数量会重叠，不能相加；这个限制直接写在页面和返回值里。
- 机器条件通过不代表事实、语义或可执行性正确；验收仍然需要人工确认。

**追问：为什么不用模型判断冲突？** 模型无法给出可复核的不可满足证明，也无法保证候选集合完整；这里需要的是可枚举、可解释、可测试的确定性结果。

## 故事四：改一句话，怎么保证没有顺手改别处

**面试官可能问**：局部改写为什么还要服务端拼接？让模型返回整段不就行了？

**回答**：

> 让模型返回整段，它可能顺手改上下文、改格式，甚至改事实。我的协议是：客户端锁定章节、版本、Unicode 码点区间和原文哈希；模型只返回 `replacement`；服务端用前缀 + replacement + 后缀自己拼接，并校验前缀、后缀、选中文字三段 SHA-256。原文或选区变化后，旧回执直接 409。前端还有一个容易踩的坑：浏览器字符串下标是 UTF-16 码元，服务端用码点；示例里 emoji 后面两种下标会相差 1，所以前端展示选区也要用 `Array.from` 按码点切。

**代码证据**：

- `ai/local_revision.py` 的 `prepare()`：冻结 block、variant、start/end、text、text_hash、revision。
- `ai/local_revision.py` 的 `run()`：只请求替换片段，并构造 `prefix_hash` / `suffix_hash`。
- `ai/local_revision.py` 的 `apply()`：重新校验 revision、当前文本哈希和可行条件，再写入。
- `proof.py` 的 `splice()` / `apply_splice()`：本页的可复现最小实现。
- `proof.py` 的 `utf16_offset()`：同时返回码点和 UTF-16 下标，页面会显示两者的偏移差。

**取舍**：

- 只支持单个连续选区，最多 1500 字；多选区和跨章节替换没有实现。
- 哈希只能证明“原文没变”，不能证明替换内容正确；内容质量仍由验收和人工核对负责。
- 服务端拼接避免了模型重写整篇，但模型仍可能生成不符合上下文语气的片段；这是能力边界，不是并发问题。

**追问：为什么不直接在前端替换？** 前端替换无法防止另一个窗口在读取和提交之间改稿；服务端必须在同一事务里复核 revision 和哈希。

## 故事五：模型作业为什么要冻结输入、记录尝试

**面试官可能问**：调用大模型失败了怎么办？会不会重复扣费？

**回答**：

> 作业提交时先冻结模型、供应商配置、输入指纹和调用上限，再进入队列。每次尝试都记录在作业结果里；失败不会静默重试，重试是用户显式发起的新的作业，带 `retry_of`。取消会检查检查点；原始响应保存在本地，公开接口只返回脱敏字段。`/proof` 的账本只展示 kind、状态、尝试/上限、模型、输入哈希和配置哈希，不展示正文或密钥。

**代码证据**：

- `ai/service.py` 的 `submit()`：校验、冻结输入、创建作业、幂等键。
- `ai/service.py` 的 `run()` / `ask()`：执行、检查取消、记录尝试。
- `ai/service.py` 的 `retry()` / `cancel()`：显式重试、取消。
- `proof.py` 的 `job_ledger()`：白名单脱敏字段。

**取舍**：

- 冻结输入让复现和审计成为可能，但配置变更后旧作业不能“续跑”，只能新建作业。
- 调用上限控制成本，但不能保证质量；真实 API 验收里仍然出现过遗漏、误判和字数不足。
- 本地单用户场景不需要分布式任务队列；多用户部署要加并发配额、持久队列和更严格的幂等存储。

## 故事六：为什么敢报告“深度模型没有更好”

**面试官可能问**：你的偏好学习效果怎么样？

**回答**：

> 我做了一个受控的离线评价：4 个合成配方场景 × 5 个模型 × 6 个随机种子 × 5 个反馈预算，共 600 次拟合；训练和查询的措辞、ID 都换掉，测试标签不进入优化。结果是内容线性模型在单段风格上约 81.5%，冻结投影搭配 84.6%，可训练投影搭配 78.2%；到搭配任务上几种方法都明显下降。所以我没有把神经模型设为默认，也没有说它全面更好。这个项目里更值得讲的是确定性的提交与约束层，偏好学习仍然是实验性模块。

**代码证据**：

- `research/content_experiment.py`：实验入口与固定种子。
- `experiments/content-latest/report.md`：完整结果、误差和学习曲线。
- `docs/TECHNICAL_LEVEL.md`：方法边界和不可外推的结论。

**取舍**：

- 合成配方和作者设计词汇只能支持受控检查，不能代替开放领域和真实用户研究。
- 48 条比较对用户是真实负担；低预算下的收益仍需试用验证。
- 面试时主动说出负结果，比声称“深度模型全面领先”更可信；但要能解释实验设计，否则会显得只是没调好。

## 三分钟演示路线

1. 打开 `/proof`，先指 hero 的 81 个候选、0 次付费调用和 5 项链校验。
2. 点“用旧版本再提交”：先成功一次，再用旧 revision 提交，展示真实 409 和 `request_id`。
3. 看默认冲突：锁定 + 必含短语 → 0 个可行搭配；冲突核两项；两组最小修正各带候选见证；敏感度 +27 / +27。
4. 把“必须保留”取消，可行数变成 27；再把上限改成 180，展示第三个条件和 0 个核外新增。
5. 到精确选区：展示码点 10–19、UTF-16 11–20 的偏移差；执行拼接，显示选区外未改变；用过期回执提交，展示 409。
6. 最后看作业账本和测试命令。账本为空也照实说：本页不发起模型调用。

## 不要这样说

- 不说“自研大模型”：这里没有训练基础模型，只有任务内的偏好模型和确定性程序。
- 不说“语义完全理解”：字面与语义定位都只是核对线索，真实 API 验收有失败记录。
- 不说“生产级分布式”：这是单机本地应用，没有鉴权、多租户和分布式共识。
- 不说“100% 不会改到别处”：哈希证明的是本次拼接的选区外文本一致，不证明内容正确。
- 不说“冲突核是最小冲突”：它是不可再删的冲突核，不保证条件数最少。

## 可能的追问与短答

**为什么用 SQLite？** 单用户、本地优先、零依赖、事务和 WAL 足够；数据量和并发都不需要服务端数据库。迁移时保留 revision CAS 和事件模型即可。

**候选爆炸怎么办？** 当前 3⁴–3⁶ 穷举是有意为之，为了精确和可解释；再大就换 CP-SAT / 分支定界，并把“精确前沿”降级为带证明界的近似。

**为什么不用现成工作流引擎？** 这里的关键不是编排，而是提交语义、快照链和有限约束求解；引入引擎不会自动带来这些保证，反而增加不可审计的中间状态。

**测试怎么做的？** 148 项 Python 检查（提交协议、快照链、约束求解、Unicode 拼接、作业生命周期、隔离沙盒与 HTTP 接口），加上隔离模拟供应商的端到端流程和 Playwright 浏览器验证；真实 API 验收单独运行，绝不混进单元测试或启动流程。

**这个项目最难的 bug 是什么？** 不是调模型，而是“状态在多个窗口、多个事件、多个哈希之间保持一致”。例如撤回目标失效、旧 revision 覆盖、UTF-16 与码点错位，任何一个都会让“看起来能用”的功能静默损坏。`/proof` 就是把这些不变量做成可现场验证的证据。
